# Bough Digital Platform — Laravel MVC + Workspace SaaS + REST API + MCP

Build a new production-ready **Bough Digital management platform** using Laravel.

This is not a prototype, static dashboard, or collection of disconnected pages. Build it as a properly structured, maintainable Laravel application following conventional Laravel MVC architecture, service-layer separation, policies, validation, queues, and tests.

The application will combine all of the following in **one Laravel codebase**:

* Workspace-based multi-tenancy
* Super Admin management
* Workspace administration
* Team/user management
* Client management
* SEO and content management
* Outreach management
* Tasks and time tracking
* Reporting
* Google integrations
* HubSpot integration
* Semrush integration
* Screaming Frog data/workflows
* S3 storage
* REST API for the portal frontend
* MCP Server for Claude/AI access
* Background queue workers
* Scheduled automation
* Audit/activity logging

The primary application domain will eventually be:

```text
https://portal.boughdigital.com
```

Workspace routes should follow the structure:

```text
/{workspace}/...
```

Examples:

```text
/bough/dashboard
/bough/clients
/bough/content
/bough/tasks
/bough/reports

/bough/api/clients
/bough/api/tasks

/mcp/bough
```

Do not build separate Laravel applications for the Portal, API, and MCP.

They must all be part of the same application and share the same:

* Models
* Services
* Authorization policies
* Validation rules
* Workspace resolver
* Database
* Integrations
* Activity logging

# 4. Workspace is the Main Tenant

The fundamental tenant entity is:

```text
Workspace
```

Everything belongs either directly or indirectly to a workspace.

Example hierarchy:

```text
Platform
│
├── Workspace A
│   ├── Users
│   ├── Clients
│   │   ├── Contacts
│   │   ├── Integrations
│   │   ├── Documents
│   │   ├── Content
│   │   ├── SEO Data
│   │   ├── Reports
│   │   └── Tasks
│   ├── Outreach
│   ├── Templates
│   └── Settings
│
└── Workspace B
    └── completely isolated data
```

Workspace isolation is a critical security requirement.

A user from Workspace A must NEVER access Workspace B data by:

* URL manipulation
* REST API
* MCP
* IDs submitted manually
* route model binding
* background jobs
* exports
* reports

Do not rely only on hiding menu items.

Enforce workspace isolation server-side.

# 5. Workspace URL Resolution

Use URLs like:

```text
/{workspace}/dashboard
/{workspace}/clients
/{workspace}/tasks
/{workspace}/reports
/{workspace}/api/...
/mcp/{workspace}
```

The `{workspace}` parameter should normally use:

```text
workspaces.slug
```

Example:

```text
/bough/dashboard
```

Create middleware such as:

```text
ResolveWorkspace
EnsureWorkspaceAccess
```

The middleware should:

1. Resolve workspace by slug.
2. Store the workspace in request/application context.
3. Verify the authenticated user is allowed to access it.
4. Reject cross-workspace access.
5. Make the workspace available to controllers, policies, services and MCP.

Do not trust `workspace_id` sent by frontend forms.

The active workspace must come from trusted application context.

# 7. Super Admin Rules

`super_admin` is PLATFORM LEVEL.

Super Admin can:

* Access global admin dashboard
* Create workspaces
* Edit workspaces
* Activate/deactivate workspaces
* View all workspaces
* Enter/view any workspace
* Manage workspace administrators
* View global system health
* View global activity logs
* View integration status
* Manage global settings
* Manage system-level MCP configuration
* Review queues/jobs
* Review failures
* Review application errors

Super Admin is the ONLY normal role allowed to:

```text
create workspace
edit workspace
delete/archive workspace
change workspace ownership
manage global platform settings
```

Super Admin routes should be separated clearly, for example:

```text
/admin
/admin/workspaces
/admin/users
/admin/system
/admin/activity
```

Do not require a workspace slug for platform administration.

# 8. Workspace Admin Rules

`admin` is WORKSPACE LEVEL.

Workspace Admin can manage almost everything inside their own workspace, including:

* Workspace users
* Team leaders
* Employees
* Writers
* VAs
* Clients
* Client contacts
* Client integrations
* Content
* Tasks
* Reports
* Outreach
* Templates
* Workspace settings that are explicitly editable

BUT:

**Workspace Admin must NOT manage the Workspace entity itself.**

They cannot:

* Create workspaces
* Delete workspaces
* Change workspace slug
* Transfer workspace ownership
* Access another workspace
* Change platform-level configuration
* Promote themselves to Super Admin
* Create Super Admin accounts

This distinction is mandatory.

# 32. MCP Authentication

MCP must require authentication.

Never create a public unrestricted MCP endpoint.

Design authentication so each MCP request resolves:

```text
Authenticated user
        ↓
Workspace
        ↓
Role
        ↓
Permissions
        ↓
Allowed MCP tool
```

Use an authentication mechanism supported cleanly by Laravel MCP.

OAuth may be introduced where required by external MCP clients.

During internal development, token authentication may be used if appropriate, but do not hardcode permanent secrets.

# 33. MCP Authorization

Every MCP tool must perform server-side authorization.

Do not assume:

```text

```

```text

requested operation
```

Example:

```text
Robert
 ↓
MCP
 ↓
update_client
 ↓
Workspace check
 ↓
Policy
 ↓
ClientService
```

Super Admin may cross workspace boundaries only through explicitly authorized platform actions.

Workspace Admin cannot use MCP to bypass the rule preventing workspace management.

# 47. Workspace-Scoped Query Safety

Create a consistent mechanism to prevent tenant leaks.

Possible approaches:

* Workspace-aware query scopes
* Service-level repository constraints
* scoped route binding
* authorization policies
* tenant context service

Do not rely solely on a global scope without considering Super Admin cross-workspace administration and queued jobs.

Create explicit architecture documentation explaining how workspace resolution works.

# 48. API/MCP Consistency

Validation and authorization rules must not diverge.

# Non-Negotiable Rules

* Laravel backend, not Node backend.
* Standard Laravel MVC.
* PostgreSQL.
* Workspace is the main tenant.
* Super Admin is platform-level.
* Only Super Admin manages Workspaces.
* Workspace Admin cannot manage Workspaces.
* Workspace Admin cannot become Super Admin.
* No cross-workspace data access.
* Client-level access restrictions must work.
* React + Tailwind portal.
* REST API and MCP in the same Laravel application.
* Shared Service layer between Web/API/MCP/Jobs.
* Laravel MCP for Claude integration.
* Redis queues for background work.
* External integrations isolated behind Services.
* Credentials encrypted.
* No generic SQL/shell MCP tools.
* Every MCP write is authorized.
* Important MCP writes are audit logged.
* Long-running MCP actions must use queues.
* Tests must prove tenant isolation.
* Do not fake functionality.
* Do not mark incomplete integrations as complete.
